# Agent guide

## Goal

Ambitious is a Grok Bot configuration and monitoring service: a free Ambitious Bot template with a daily analysis that stays in the owner's account, the Ambitious Bot plan, $725/month per bot, for a person's review of each report, and open-source single-purpose CLI modules with no UI that the bot drives. This repo is the kit those modules are built from: the module contract, the shared code and contract tests, the lint and dependency rules, and the repo template. Everything here is copied into every module, so a change is good when it makes every module safer or simpler for the bot that drives it.

## How to work

- Work in small steps and prove each one: say what the change must do, make the smallest change that does it, then run the checks and show their output. Model choices per agent role are in `.cursor/rules/agent-models.mdc`. Claude Code analysis runs use `--model claude-fable-5-2`.
- Trust in this order: types and API design, then lint and the dependency graph, then tests and verification, then prose.
- When you are corrected, turn the correction into a lint rule with a fix-the-root-cause message or into an API change. Do not add it to this file.
- When a check fails, fix the cause. Never weaken or skip a check to make it pass.

## Data shape

- The contract is `MODULE_CONTRACT.md`. The envelope every module prints is `schemas/envelope.v1.json`.
- The lint bans are one table, `packages/lint/src/bans.ts`: what is banned, the fix message, and the directories where it is allowed.
- The dependency rules are one list, `forbidden` in `packages/depcruise/src/config.ts`.
- The repo template is the files under `repo-template/`, copied by `scripts/apply-template.mjs`.
- The bot template is the files under `template/`. Its pins are one list, `template/modules.lock.json`; `template/bot.json`, the `Template version` line of every skill, and the installer pin in the `ambitious-module-installer` skill are generated by `npm run template:generate`. `template/INSTRUCTIONS.md` is written by hand and carries `Instructions version: N`; every published text, with its SHA-256, what it grants and the reason for each grant beyond the oldest supported text, is one list, `versions` in `template/instructions.json`, and what each skill and routine needs is `template/permissions.json`. Every routine prompt a release published is recorded in `template/routines.json`. The files under `template/fixtures/`, every skill body and every guide under `template/guides/` are embedded in the installer, which writes the skills out with `skill-files` and prints a guide with `guide`. A skill is a short job description with its hard rules; reference text belongs in a guide. The size budget for the skills and routine prompts is one constant, `TEMPLATE_BUDGET` in `packages/kit/scripts/template-budget.mjs`, a conservative budget and not a measured platform limit.
- The shared code is `packages/kit/src/`, one name per file with no index file, and its Python mirror `packages/kit-python/ambitious_kit/`. A change to one is a change to both.
- What a user can rely on is the list in `verify/features.json`; `verify/run` proves each entry.

## Directory boundaries

- `packages/lint/`: `@ambitious/lint`, the ESLint config and rules, plus the Python comment checker in `python/`.
- `packages/depcruise/`: `@ambitious/depcruise`, the dependency-cruiser config.
- `packages/kit/`: `@ambitious/kit`, laid out like a module (`src/cli`, `src/domain`, `src/db`, `src/install`) so the same rules hold for it. `packages/kit-python/`: the Python mirror.
- `examples/hello/`: a complete module on the kit. Keep it the smallest thing that exercises every rule.
- `repo-template/`: the files every repo gets. `template/` is the Ambitious Bot template (instructions, skills, routines, module pins) and is not this.
- `src/`, `spec/`, `test/`, `verify/`: the same layout every module has.
- `schemas/`, `examples/`: the machine-checked parts of the contract.

## Judgment calls

- Whether a rule belongs in the kit: only when every module needs it. A rule for one module lives in that module.
- What a rule's message says: where the code should move, not only what is wrong. Someone reading it should be able to fix the cause without opening this repo.
- How to prove a rule: a fixture that fails with the message and clean code that passes. A rule with no failing fixture is not done.
- How strict to be when a module's own documentation and `MODULE_CONTRACT.md` differ: follow the stricter one and say so in the PR under `## Decisions`.
- How much to build: the smallest change that meets the goal. Delete before you add. Every line here is copied many times.
- Wording: keep code and docs generic for every kind of organization. No person, bot or customer names, no industry terms, and no compliance or security claim beyond what the code enforces.
